## 🔴 P0 — 真实 Bug

### B1. `CommentRepository.create()` 在"视频被并发删除"时返回 500，而非 404 ✅ 已修复

`CommentService.postComment()` 先 `videoExists()` 校验（第 56 行），再 `create()`。虽然 `create()` 用子查询做了 TOCTOU 守卫（很好），但 `affectedRows == 0` 时抛的是 **`IllegalStateException`**：

```java
// CommentRepository.java:106-108
if (affectedRows == 0) {
    throw new IllegalStateException("video not found or deleted: " + videoId);
}
```

`GlobalExceptionHandler` 没有针对 `IllegalStateException` 的 handler，它会落入兜底的 `handleUnexpectedException` → **HTTP 500 + `log.error` 打印完整堆栈**。从用户视角，"对一个刚才还能看到的视频发评论"会得到服务端错误；从运维视角，每次并发删除都会产生一条 ERROR 日志，污染告警。

**建议：** 让 Repository 抛业务异常，或由 Service 捕获转换。

```java
// 方案 A（推荐）：Service 层捕获，语义最清晰
// CommentService.postComment()
try {
    Comment comment = commentRepository.create(videoId, currentUserId, content);
    ...
} catch (IllegalStateException e) {
    throw new BusinessException(ErrorCode.VIDEO_NOT_FOUND);
}
```

```java
// 方案 B：Repository 直接抛业务异常（更少代码，但 Repository 依赖 common 包）
if (affectedRows == 0) {
    throw new BusinessException(ErrorCode.VIDEO_NOT_FOUND);
}
```

> 同样的隐患存在于 `VideoRepository.create()` 第 223 行（创建后视频查不到）和 `UserRepository` 第 76 行，但那些是"几乎不可能发生"的内部错误，500 可接受；评论这个是**正常并发场景**，必须修。

## 🟠 P1 — 性能 / 设计隐患

### P1.1 推荐流 `NOT EXISTS` + 实时 COUNT 在大数据量下会慢 ✅ 已加注释

`RecommendRepository.INNER_SQL` 现在是：

```sql
SELECT v.id, (SELECT COUNT(*) FROM video_likes WHERE video_id = v.id) AS like_count, v.created_at
FROM videos v
WHERE v.status='published' AND v.visibility='public' AND v.deleted_at IS NULL
  AND NOT EXISTS (SELECT 1 FROM video_views vv WHERE vv.user_id=? AND vv.video_id=v.id)
```

Review04 把 `like_count` 改为实时 COUNT 后，**每个候选视频都要跑一次 `COUNT(*)`**，且 `idx_videos_recommend` 索引（`like_count DESC`）因列始终为 0 而完全失效——优化器只能全表扫描 `videos` 再对每行做关联子查询。

课程演示数据量小看不出来，但这是真实性能退化。**两个可选方向（任选其一）：**

1. **恢复反规范化计数器 + 事务内同步**（最高性能）：`like/unlike` 时在事务里同时 `UPDATE videos SET like_count = like_count ± 1`，删除视频时同步减。Review04 为了"消除漂移"改实时，但其实漂移可以用事务+单点更新杜绝。
2. **保留实时 COUNT 但加 `LIKE_COUNT` 物化视图/定时刷新**——课程项目过度。

> 我的建议：P0 演示用，**保留实时 COUNT 没问题**（数据量小、语义简单）；但要在文档里明确标注"当前实现牺牲索引效率换取一致性，生产环境应恢复反规范化计数器"，避免被答辩老师追问。这点 `idx_videos_recommend` 索引现在形同虚设，**建议在 schema 注释里说明**。

### P1.2 `GET /comments` 和 `POST /comments` 每次都多查一次 `videoExists` + `countByVideoId` ✅ 已修复

`getComments()` 调用了 3 次 DB：`videoExists` → `findByVideoId` → `countByVideoId`。其中 `videoExists` 与 `findByVideoId` 语义重叠（视频不存在时 `findByVideoId` 自然返回空）。`postComment` 同理。

**建议：** 删除冗余的 `videoExists` 预检查，改为：列表为空时再用一次 `videoExists` 区分"视频不存在"和"视频无评论"。

```java
// CommentService.getComments() 简化
List<Comment> comments = commentRepository.findByVideoId(videoId, pageCursor, pageSize + 1);
if (comments.isEmpty() && pageCursor == null && !commentRepository.videoExists(videoId)) {
    throw new BusinessException(ErrorCode.VIDEO_NOT_FOUND);
}
```

这样"有评论的视频"省一次查询，"无评论的视频"查询次数不变。

### P1.3 `commentRepository.videoExists` 与 `videoRepository.videoExists` 重复定义 ✅ 已修复

两个 Repository 各有一份完全相同的 `FIND_VIDEO_EXISTS_SQL`。这是复制粘贴，未来 schema 变更（比如 `status` 判断）容易漏改一处。

**建议：** 删除 `CommentRepository.videoExists`，复用 `VideoRepository.videoExists`（在 `CommentService` 注入 `VideoRepository`）。

## 🟡 P2 — 健壮性 / 小问题

### S1. `CommentPageCursor` 游标解码用 `LocalDateTime.parse`，但编码用 `toString()` ✅ 已修复

```java
// CommentService.java:162, 155
String value = comment.createdAt() + "|" + comment.id();   // toString()
... LocalDateTime.parse(parts[0]);                          // parse()
```

`LocalDateTime.toString()` 在秒/纳秒为 0 时会省略部分（如 `2026-06-15T00:00`），而 `parse` 能兼容。**目前能正常往返**，但这是隐式契约。建议统一用 `DateTimeFormatter.ISO_LOCAL_DATE_TIME` 显式格式化，或在单测里加一个往返测试锁定行为。

### S2. `normalizeLimit` 拒绝 `limit=0`，但错误信息不友好 ✅ 已修复

```java
if (limit < 1 || limit > MAX_LIMIT) {
    throw new BusinessException(ErrorCode.INVALID_PARAMETER, "invalid limit");
}
```

建议把范围写进 message：`"limit must be between 1 and " + MAX_LIMIT`。

### S3. `BearerAuthenticationFilter` 的 `requiresAuthentication` 是硬编码白名单

每加一个需鉴权的端点都要改这个方法，已经积累了 11 条规则。**这是已知技术债**（课程项目可接受），但要注意：当前 `isVideoActionPath(path, "")` 对 `DELETE /api/v1/videos/{id}` 放行任意数字 id，没有校验 id 是否合法 long——非法 id（如 `/api/v1/videos/abc`）会被 Spring 在 `@PathVariable long videoId` 处先拒绝（400），所以**目前安全**，但依赖了 Controller 层兜底。无需改动，知晓即可。

### S4. `video_views` 表既是"访问历史"又是"推荐去重依据"，语义耦合 ✅ 已加注释

当前 `recordView` 只在 `POST /views/me` 调用（已确认未在点赞/评论路径调用），所以**目前没 bug**。但这是一个脆弱的设计：一旦未来有人在"用户点开评论"时也调 `recordView`，就会把"看过评论的视频"也算作"已访问"，从而从推荐流消失。建议在 `video_views` 或 `RecommendRepository` 附近加注释，写明"`video_views` 一行 = 该用户已刷到过该视频，推荐去重依赖此语义，禁止在非访问场景写入"。

### S5. `RecommendRepository` 游标已修复，但建议加单测锁定

提交记录显示成员 B 修过游标。当前 `CURSOR_CLAUSE` 三段式（`like_count < ?` / `=` + `created_at <` / `=` + `id <`）是正确的。**建议补一个边界测试**：构造 like_count 相同、created_at 相同、仅 id 不同的多条视频，验证翻页不漏不重。这块一旦回归很难发现。

### S6. `Comment.content` 用 `VARCHAR(300)`，但 `MAX_CONTENT_LENGTH = 300`

```java
private static final int MAX_CONTENT_LENGTH = 300;  // Java 按 UTF-16 char 计数
// schema: content VARCHAR(300)  // MySQL 按 utf8mb4 字符计，emoji=1 char，OK
```

`String.length()` 是 UTF-16 code unit 数，emoji（ surrogate pair）算 2；MySQL `VARCHAR(300)` 算字符数算 1。所以 Java 限制比 DB 更严，**不会溢出**，方向安全。但 `content.trim()` 后长度判断发生在 trim 之后，没问题。无需改动，仅确认。
