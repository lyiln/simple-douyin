## 4. 合并与审查规则

| 环节 | 规则 |
| --- | --- |
| 分支 | 每个任务单独分支，建议命名为 `feature/T13-like`、`feature/T15-grpc-recommend` 等 |
| 自测 | 开发负责人提交前必须运行本任务相关测试；后端任务至少运行 `mvn -q test`、`git diff --check`、`git diff --name-only -- frontend` |
| 审查 | 不能自审；主审人必须检查 API 契约、权限、日志、测试和是否越界实现 Bonus |
| 合并 | 成员 C 负责合并协调；只有主审通过且检查命令通过后才能合并 |
| 冲突 | 合并冲突先由任务负责人解决，再由主审复核，最后成员 C 合并 |
| 记录 | 每次合并后更新 `README.md` 或 `docs/progress.md` 中的实际进度 |

## 5. 审查重点

| 审查项 | 检查内容 |
| --- | --- |
| 范围控制 | 是否只做当前任务，不提前实现 Bonus 或后续接口 |
| 权限 | 需要登录的接口是否必须 Bearer Token；用户隔离是否正确 |
| 数据一致性 | 点赞数、浏览数、评论数、软删除、分页游标是否稳定 |
| 推荐规则 | 是否按 `like_count DESC, created_at DESC, id DESC`，是否过滤已访问视频 |
| gRPC | 推荐流 REST 是否通过 gRPC Recommend Service 获取 videoIds |
| 日志 | request_logs 是否记录输入、输出、耗时、userId、业务码；敏感字段是否脱敏 |
| 测试 | 正常、异常、权限、幂等、日志、推荐规则是否覆盖 |
| 前端联调 | Android 是否使用真实 API，不把本地 mock 当作最终效果 |
| 交付材料 | README、需求、技术设计、测试文档、PPT、团队分工、成员评分表、演示视频是否齐全 |
