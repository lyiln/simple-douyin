# 需求文档

## 1. 项目背景

本项目为《API 设计与实现》课程期末大作业，主题为“简易版抖音 / 视频流推荐系统”。项目围绕短视频应用的核心业务闭环进行设计与实现，重点考查 REST API 设计、后端分层、数据库设计、RPC 服务调用、认证与权限控制、请求日志和客户端演示能力。

项目不追求复刻完整商业短视频平台，而是以课程要求为边界，实现账号、视频发布、推荐浏览、访问过滤、点赞、评论、个人视频管理等关键能力。主要提交物为本地源代码和项目文档；Android 客户端作为主要演示端，`web/` 中的 React 客户端作为本地补充演示端。服务器仅作为答辩期间可开启的演示环境，不作为长期生产环境。

## 2. 项目目标

项目目标如下：

1. 提供注册、登录、退出和当前用户信息查询能力，建立可识别当前用户的账号体系。
2. 提供视频发布、分页查看我的视频和删除本人视频能力，形成作者侧内容管理闭环。
3. 提供基于 gRPC 的简化推荐链路，按点赞关系数量和发布时间排序，并过滤用户已访问的视频。
4. 提供视频上下滑动、点赞、查看评论和发表评论等短视频核心交互。
5. 使用 MySQL 8 保存用户、视频、点赞、访问、评论和请求日志数据。
6. 记录 REST 请求的输入、输出、状态和耗时，并提供 API Server、MySQL、推荐服务的健康检查。
7. 通过认证、资源归属校验、密码哈希、日志脱敏和上传校验满足课程要求中的基础安全检查。
8. 形成可用于本地提交和答辩演示的 Android、Web 与后端项目，并使用仓库内 Docker/Compose 材料支持答辩服务器部署；不将其表述为长期生产体系。

## 5. 核心业务场景

### 5.1 场景一：推荐视频 / 刷视频 → 点赞 → 查看评论 → 提交评论

目标流程：

```text
登录用户进入视频首页
  -> 获取推荐视频
  -> 上下滑动切换视频
  -> 记录视频访问
  -> 点赞或取消点赞
  -> 打开评论列表
  -> 提交评论
```

后端已具备推荐、访问记录、点赞、评论等完整 API 和数据库能力。推荐接口通过 API Server 调用 gRPC Recommend Service，推荐服务从 MySQL 查询公开、已发布、未删除且当前用户未访问的视频，按照实时点赞关系数量、创建时间和视频 ID 倒序返回。

Android 端当前由 `MainActivity` 启动 `RealDouyinApp`，登录后调用推荐接口加载视频；视频可见时上报访问，点赞和评论直接调用后端。Web 端也实现推荐加载、访问上报、点赞和评论抽屉，可作为浏览器补充演示。两端均依赖后端、MySQL 和 gRPC 推荐服务可用。

### 5.2 场景二：登录 / 注册 → 发布视频 → 我的列表 → 删除视频

目标流程：

```text
用户注册或登录
  -> 获取 Bearer Token
  -> 发布视频
  -> 分页查看我的视频
  -> 删除本人视频
```

后端已实现注册、登录、退出、multipart 视频发布、我的视频游标分页和删除权限控制。视频文件保存在 API Server 的本地 `uploads/` 目录，视频记录保存在 MySQL。删除时校验当前用户是否为视频作者，成功后执行软删除；对他人视频的删除请求返回禁止访问错误。

Android 端已经提供注册/登录页、multipart 发布页和真实个人作品列表，并调用删除及退出接口；Web 端也覆盖相同流程。Android 发布素材先由 `PublishAssetRepository` 准备为本地文件，再通过 `ApiRepository.publishVideoFile()` 上传，这属于真实后端上传链路，不是仅在内存中添加作品。

## 7. 非功能性需求

### 7.1 安全性

- 密码必须使用 BCrypt 哈希后存入数据库，不保存明文密码。
- 需要登录的接口必须校验 `Authorization: Bearer <token>`。
- 删除视频必须校验视频作者与当前用户一致。
- 请求日志中的 password、token、authorization、secret 等字段必须脱敏。
- multipart 文件必须校验大小、MIME 类型，并使用服务端生成文件名避免路径穿越。
- 答辩或服务器演示环境中的数据库密码、token secret 和服务器地址不直接写入公开文档，使用环境变量或占位符表示。

### 7.2 性能与容量控制

- 推荐流和我的视频默认每页 10 条，最大 30 条；评论默认每页 20 条，最大 50 条。
- 推荐、视频和评论分页使用游标，避免页码分页在数据变化时产生明显重复或遗漏。
- 上传视频默认最大 100MB，封面默认最大 10MB。
- 当前未进行可公开复核的压力测试，因此不声明具体吞吐量或并发性能指标。

### 7.3 可用性与可维护性

- 提供 `/api/v1/health` 检查 API Server、MySQL 和 gRPC 推荐服务状态。
- 后端按 Controller、Service、Repository、DTO/Model、Config/Common 分层，降低接口、业务和数据访问的耦合。
- 统一响应和统一异常处理确保客户端能够按照 HTTP 状态码和业务码处理错误。
- 关键配置使用环境变量覆盖，便于在本地和答辩服务器之间切换。

### 7.4 数据与日志

- MySQL 8 使用 `utf8mb4`，支持中文昵称、视频标题和评论。
- 点赞、访问使用用户与视频唯一关系保证幂等。
- 视频使用软删除，避免直接移除业务记录。
- 请求日志写入数据库失败时不应中断主业务请求。

### 7.5 部署要求

- 今晚提交以本地代码、SQL 和文档为主。
- 本地运行依赖 Java 17、Maven、MySQL 8 和 Android 开发环境。
- 答辩当天可将后端部署或启动在演示服务器，Android 端连接演示地址进行展示。
- 服务器为答辩演示环境，非演示时间可能关闭，不承诺长期在线或生产级 SLA。
- 仓库提供 API Server/Recommend Service Dockerfile、MySQL + 两个后端服务的 Compose 和离线镜像部署手册；仅作为答辩演示部署能力。
- 仓库未发现 Nginx 和 CI/CD 配置，不将反向代理、自动构建或自动发布列为已实现。

7. 现有测试代码覆盖后端主要模块，但本次文档更新未运行测试；最终测试结论应以实际命令和 Surefire 报告为准。
